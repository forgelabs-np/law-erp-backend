# 2026-09-19

## System config hardening + yml→DB settings migration

Asked "is one `system_config` table holding both GLOBAL and FIRM scopes good practice?" —
verdict: yes, one table is right (identical shape + metadata, and `getEffectiveConfig`
needs both scopes at once), but the implementation had real holes. Fixed them all.

### Bugs fixed

- **Duplicate GLOBAL rows could crash every config read.** `UNIQUE(scope, firm_id, config_key)`
  never protected GLOBAL rows because Postgres treats NULLs as distinct, and
  `Collectors.toMap` threw `IllegalStateException` on a duplicate — that would take out
  *all* outbound email, not just the duplicated key. Replaced with a `toValueMap()` helper:
  newest `updated_at` wins, duplicates logged. Added partial unique indexes in
  `V2026_09_19_1__system_config_scope_uniqueness.sql` (run manually, like other migrations).
- **An undecryptable value NPE'd the whole map.** `decryptIfNeeded` returns `null` on
  failure and `toMap` throws NPE on a null value, so a changed `config.encryption.key`
  broke every email. Now the bad row is skipped with a warning naming the key — matters
  right before pointing the prod profile at a fresh database.
- **`APP_PRODUCTION` was a ghost toggle.** Seeded and rendered in the Super Admin settings
  UI, but nothing read it; `TotpUtil` used `app.production` from yml. So a super admin
  could flip "Production: Y", get a success response, and the `123456` MFA bypass stayed on.
  Now `TotpUtil` reads `SystemConfigService.productionFlag()` (DB first, yml fallback) and
  the *seed* default is derived from `app.production`, so seeding a prod DB can't ship the
  bypass enabled. `TotpUtil` moved to constructor injection for this.
- **Firm admins could write arbitrary config keys.** `PUT /api/v1/firm/config` took any key,
  and `getEffectiveConfig` merges FIRM over GLOBAL — so `LOGIN_URL` / `CLIENT_PORTAL_URL`
  could be repointed at an attacker page *inside real password-reset emails*. `setValue` now
  refuses keys the registry doesn't declare for the scope, the URL readers use `getGlobal`
  only, and URL-type values are validated as http(s).
- **A new firm's settings screen was empty.** FIRM registry keys are `seed=false` and
  `getFirmSettings` only read rows. It now falls back to registry defaults for missing keys.
- **A trial firm could be created with no expiry.** `isTrial` + null `trialDays` skipped the
  expiry block, and `TrialExpiryScheduler` skips null expiry → an eternal trial. Falls back
  to `TRIAL_DEFAULT_DAYS` now. (The old seed-count assertion also caught my own miscount of
  `seed=true` entries — 12, not 11.)

### Settings moved out of application.yml into the registry

- `security.max-login-attempts` → `LOGIN_MAX_ATTEMPTS`; new `LOGIN_LOCK_MINUTES` (the 30-minute
  lockout was hardcoded in `handleFailedLogin` *and* in the user-facing error message).
  Removed the yml key from all three profiles.
- `app.production` → `APP_PRODUCTION` (yml kept as boot fallback only, with a comment saying so).
- New keys for previously hardcoded values: `TRIAL_DEFAULT_DAYS` (14), `TRIAL_WARNING_DAYS`
  (was `daysRemaining <= 3`), `NOTIFICATION_MAX_ATTEMPTS` (was `static final MAX_ATTEMPTS`),
  `LOGIN_URL` / `CLIENT_PORTAL_URL` (were literals inside `EmailServiceImpl`).
- Deliberately left in yml: `jwt.*` (read once at construction — DB-driving buys nothing),
  `config.encryption.key`, DB/mail/hikari, `cors.allowed-origins`, `permissions.cache.ttl-ms`.
  Later candidate if wanted: `scraper.*` via `ScraperProperties`.

## Two-table split (asked for after the hardening pass)

User pushed back on one table holding both scopes — "default setting is also there, per
firm setting is also there" → wanted them physically separate for manageability. Agreed:
the integrity wins of two tables (NOT NULL firm_id, real FK/cascade, no scope column that
can lie) mostly come from the split, and it stops a GLOBAL row from silently sitting next
to 30 firms' overrides.

- `system_config` is now GLOBAL-only: `scope` + `firm_id` columns dropped, `ConfigScope`
enum deleted, unique on `config_key` alone.
- New `firm_configs`: `FirmConfig` entity, `FirmConfigRepository`, `FirmConfigService`
(owns the 5 FIRM keys, its own allowlist, registry-default fallback, and
`getEffectiveConfig(firmId)` = firm over platform).
- `ConfigKeyRegistry` (`common/config`) now declares every key once, split into `GLOBAL`
and `FIRM` lists, plus shared `SettingDef` + RADIO/NUMBER/URL validation. It references the
services' key constants — safe because they are compile-time `static final String`s, so no
class-init cycle.
- `system_config` uniqueness hole is now structurally gone (no nullable discriminator):
straight `UNIQUE(config_key)` + `UNIQUE(firm_id, config_key)`. The
`V2026_09_19_1` partial indexes are superseded and that migration is now only needed for a
database that has not yet run the split.
- Migration `V2026_09_19_2__split_firm_config_table.sql`: creates the table, copies
`scope='FIRM'` rows (ON CONFLICT DO NOTHING), then drops the columns. Run manually, verify
the two counts before the drops.
- Tests: `FirmConfigServiceTest` added (11 tests); `SystemConfigServiceTest` rewritten for
the GLOBAL-only API; `MeServiceTest` mocks `FirmConfigService` now. **382 green.**

## Sub-module permissions ("cannot assign permission to sub-module")

Traced the whole chain before touching anything:

- Permission plane was already fine — `POST /admin/modules/{id}/permissions` and
  `PermissionServiceImpl.upsert` work for any module, `linkPermissionToModule` links a custom
  permission to a sub-module by code, `GET /admin/permissions/grouped` lists sub-modules as
  their own groups (no parent filter), and the SA override
  `PUT /super-admin/firms/{id}/roles/{roleId}/permissions` has no ceiling check.
- **The break was the module-access plane.** `PermissionEvaluator.hasModuleAccess` did a direct
  `firm_modules` lookup by module code, while `/me`'s sidebar marks a sub-module enabled when
  its parent is. So TESTCONFIG1 showed in the menu and then 403'd with "Module not enabled for
  your firm. Please upgrade your plan."
- Enabling a parent never wrote rows for its children, so the SA had no way to see or grant them.

Fix — one rule in one place, `ModuleAccessResolver` (pure/static, so it is unit-testable):

- Nearest ancestor-or-self `firm_modules` row decides; an explicit child row wins; expiry still
  disables. Used by `PermissionEvaluator`, `FirmModuleServiceImpl.isModuleEnabled`, the new
  `resolveEnabledModules(firmId)` and `MeServiceImpl`'s sidebar (which reuses the rows it
  already fetched, so no extra query).
- `enableModuleForFirm` now cascades to the whole sub-tree in both directions, so granting
  TESTCONFIG grants TESTCONFIG 1 / 2, they show up in `GET /super-admin/firms/{id}/modules`, and
  each can be switched off individually afterwards.
- Tests: `ModuleAccessResolverTest` (7) + `FirmModuleCascadeTest` (3). **392 green.**
- Still open if wanted: `getFirmModules` only returns explicit rows, so a sub-module created
  *after* a grant is accessible (inherited) but has no row in that listing yet.

## "Emails are not going" — diagnosis

`sendHtmlEmail` catches everything and only logs/audits, so nothing surfaces to the caller.
`resolveMailSender` order: firm `firm_email_configs` (active) → GLOBAL `SMTP_HOST` +
non-empty user **and** pass → `defaultMailSender` from application yml.

Most likely causes, in order:

- **Dev default sender is a dead end.** `application-dev.yml` has `MAIL_PASS:` (empty) and
  `MAIL_USER: noreply@nepalcrm.com`. `.env` has no `MAIL_*` keys at all, and Spring does not
  read `.env` — so unless MAIL_USER/MAIL_PASS are real env vars or a DB SMTP row exists,
  Gmail auth fails (`535 Username and Password not accepted`).
- **From-address mismatch.** `resolveFromAddress` falls back to the authenticated username;
  with the dev defaults that's `noreply@nepalcrm.com`, which a personal Gmail account cannot
  send as (`553 sender address rejected`) — fails even with a valid app password.
- **Half-set GLOBAL SMTP keys** silently fall through to the broken default (needs BOTH user
  and pass non-empty). A `SMTP_PASSWORD` written under a *different* `config.encryption.key`
  now reads as empty instead of throwing — same fallback, different cause.
- Port stored non-numeric → `NumberFormatException` on `SMTP_PORT`.

Where the reason is visible: log line `EMAIL_FAILED:` and `audit_logs` rows with action
`EMAIL_FAILED`. Both now log the **root cause** instead of JavaMail's generic
"Authentication failed" (`rootCause()` helper added in `EmailServiceImpl`).

Prod note: `application-prod.yml` uses `${MAIL_HOST}` etc. with **no defaults**, so a missing
`MAIL_*` env var stops startup; and a fresh prod DB has no SMTP rows at all. Also set
`LOGIN_URL` / `CLIENT_PORTAL_URL` — they seed to `app.nepalcrm.com`.

## CONFIGURATION module + docs

- Added `CONFIGURATION` parent module (displayOrder 18, icon `SettingsIcon`, path `/settings`)
  with two sub-modules: `GLOBAL_CONFIG` and `FIRM_CONFIG`.
- Each sub-module has permissions: ACCESS, VIEW, EDIT, DELETE.
- Role matrix: SA = FULL on both; FIRM_ADMIN = READ_ONLY on GLOBAL_CONFIG, FULL on FIRM_CONFIG;
  all others = NO_ACCESS.
- `FirmConfigController` now checks `FIRM_CONFIG:VIEW` / `FIRM_CONFIG:EDIT`;
  `SuperAdminConfigController` checks `GLOBAL_CONFIG:VIEW` / `GLOBAL_CONFIG:EDIT` / `GLOBAL_CONFIG:DELETE`
  and `FIRM_CONFIG:VIEW` / `FIRM_CONFIG:EDIT` for per-firm endpoints.
- Created `docs/config-setup.md` — full reference: all keys, API endpoints, RBAC matrix,
  security invariants, consumer code patterns, and a complete frontend integration guide
  (React/TypeScript) with form rendering, validation, permission-gated UI, and sensitive field handling.
