### D6 — login now names the real reason, without becoming a username oracle
`GlobalExceptionHandler` already surfaced `ex.getMessage()` (2026-10-06), but that turned
`/auth/login` into an **account-enumeration oracle**: the inactive/blocked/portal-disabled/
wrong-door checks all ran *before* the password was compared, so any firm code + username leaked
account existence and type to an unauthenticated caller.

`AuthServiceImpl.performAuthentication` was reordered:
1. firm lookup + suspended/expired (firm-level, caller supplied the code — safe to name),
2. user lookup → generic `Invalid credentials`,
3. `assertNotLocked` — **before** the password so a locked account cannot burn more attempts, and
   safe to name because the caller caused the lock,
4. **`passwordEncoder.matches`** proves the password → generic `Invalid username or password` on
   failure (`handleFailedLogin` counts the attempt),
5. only now: inactive / blocked, then wrong-door (`Super admin must use /super-admin/login`,
   `Clients must sign in through the client portal`, `This account is not a client account`) and
   portal-disabled — all named.

**Why `passwordEncoder.matches` replaced `AuthenticationManager.authenticate`:** Spring's
`DaoAuthenticationProvider` throws `DisabledException`/`LockedException` in its *pre*-authentication
checks, i.e. **before** the password is compared, which would make every state reason unreachable.
Proving the password ourselves also fixes a latent bug: the provider looked the user up with the
global `findByUsername` while this flow had already resolved the **firm-scoped** user, so two firms
sharing a username could authenticate against the wrong row. `AuthenticationManager` is now unused
in `AuthServiceImpl` (removed with its imports).
- Split `validateAccountStatus` into `validateAccountStatus` (inactive/blocked, called post-password)
  + `assertNotLocked`/`lockoutMinutesRemaining` so the lock gate can run earlier; the MFA path keeps
  the lock check.
- New regression probes in `E2eSecurityConfigProbeTest`: FINDING-4a (locked account is told, with
  the length), FINDING-4b (portal-disabled client: generic on a wrong password, named on the right
  one), FINDING-4c (inactive account: same shape), FINDING-5 (client forced rotation, end to end).
  Probe suite now 7 tests; FINDING-2's stale "handler masks everything" comment corrected.
- **Gotcha found while writing those probes:** the QA harness's `createUser` helpers store the
  password **raw**, so a helper-created user can never password-authenticate (`BCryptPasswordEncoder`
  returns false for a non-hash). `4b`/`4c` create their users through the API instead.

### MFA_DEV_BYPASS moved into `system_config` (user reminder: "we have systemconfig for all configurable configs")
- The 2026-10-06 session made the dev TOTP bypass yml-only. That broke the standing convention
  ("never bury a tunable in `application.yml` only"), so it is now a declared config: new
  `MFA_DEV_BYPASS` key in `ConfigKeyRegistry` (SECURITY, RADIO `Y,N`, **`seed=false`**) with
  `SystemConfigService.mfaDevBypassFlag()` returning `Optional<Boolean>`, and `TotpUtil` reading it as
  `mfaDevBypassFlag().orElse(ymlDevBypass)` — the same pre-seed-fallback pattern as `APP_PRODUCTION`.
  `seed=false` keeps a dev database working with no row; production mode still blocks the bypass
  regardless of what the DB says.
