# 2026-10-05

## E2E pass: super admin → firm admin → employee/client, and 3 fixed bugs

- Added `FullLifecycleE2ETest` (`src/test/java/.../integration/`) — drives the whole journey over
  **real HTTP with real logins** (no directly-minted JWTs): SA register → MFA setup confirm (dev
  code `123456`) → create firm → enable every module via API → grant FIRM_ADMIN → firm admin's
  first-login forced rotation + MFA → grant ADVOCATE → create employee → employee rotation login →
  create client + project → client portal login. Also exercises matter create/assign, scoped
  employee matter list, document upload (FakeStorageService config), dashboards, calendar, audit
  surfaces. Passes.
- Why it is new coverage: the existing integration/QA suites mint tokens directly and set modules
  by DB, so the `register → MFA → forced rotation → access token` chain was never exercised end to
  end. This is why the three bugs below were invisible.

Three real defects found by probes (`E2eSecurityConfigProbeTest`) and fixed:

1. **Multiple super admins allowed.** `SuperAdminServiceImpl.registerSuperAdmin` guarded by
   `existsByUsernameAndUserType(...)`, not by "any SA exists", so a second SA with a different
   username/email/mobile registered successfully — contradicting the app's own
   "Only one super admin allowed." Fixed: `countByUserType(SUPER_ADMIN) > 0` → 400.
2. **Login-lockout settings were dead config.** `SystemConfigService.loginMaxAttempts()` /
   `loginLockMinutes()` were never called anywhere; `AuthServiceImpl` used
   `@Value("${security.max-login-attempts:5}")` (that key is absent from every yml → always 5) and a
   hardcoded 30-minute lock. So the admin Settings UI's `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCK_MINUTES`
   had no effect — a direct violation of the standing "runtime changes live in `system_config`"
   rule. Fixed: both values now read from `SystemConfigService`.
3. **Replayable first-login password-change token.** `/auth/change-password` accepted any valid
   `pwd_change` token regardless of `mustChangePassword`, so a captured token could change the
   password again within its 10-minute life (probe changed it twice, both 200). Fixed: reject once
   `mustChangePassword` is false (single-use).

Not fixed (product decisions, reported):

- `GlobalExceptionHandler.handleBadCredentials` collapses **every** `BadCredentialsException` into
  "Invalid username or password", so "Account locked. Try again in 30 minutes.", "Your account is
  inactive", "firm account suspended" and "portal access is disabled" are never shown to the user.
  Fine as anti-enumeration, but the intent in the service is currently dead — the lockout probe had
  to assert on the DB row, not the response body.
- `ClientServiceImpl.createClient` does **not** set `mustChangePassword`, so a client keeps the
  password the firm admin chose for them, while firm admins and employees are forced to rotate.

Tests: **616 → 620 green** (1 E2E + 3 regression probes). Source changes uncommitted on `devG`.

## Same day — document upload failed on PostgreSQL: an unrun migration + an orphaned-object leak

- Symptom: `INSERT into matter_timeline (... event_type='DOCUMENT_UPLOADED')` → SQLState `23514`,
  violates `matter_timeline_event_type_check`.
- **Not** caused by the auth fixes above. Root cause: `V2026_09_28__document_store_constraints.sql`
  was never applied to the Supabase dev DB. Hibernate `ddl-auto=update` writes enum CHECK
  constraints only when it creates a table and never alters an existing one. Constraint went from
  **13 values (before)** to **14 incl. `DOCUMENT_UPLOADED` (after)** — proved over JDBC by printing
  `pg_get_constraintdef` before/after and by a rolled-back `DOCUMENT_UPLOADED` insert that is now
  accepted. Credentials were read from `application-dev.yml`, never echoed.
- Secondary bug fixed in `DocumentServiceImpl.upload`: the comment promised "any failure below must
  remove the object", but the final `documentRepository.save` + `recordTimeline` + `toResponse`
  block was unguarded, so a failure after `storageService.put` left the object orphaned in the
  bucket (quota rolled back, bytes kept). Now wrapped in try/catch → `discard(storageKey)`.
  Regression test `discardsWhenTimelinePersistenceFails`.
- Added `MigrationConstraintDriftTest`: every `TimelineEventType` and `PermissionAction` value must
  appear quoted in some `db/migration/*.sql`, so an enum addition without a migration fails the
  build instead of the live PostgreSQL. (`PermissionAction` had **no** drift.)
- Tests: 620 → **623 green**.

## Same day — repo-wide comment strip (src/main Java)

- Scope chosen by the user: **only `src/main/java`**; keep only short single-line “why/hazard”
  comments; no multiline comments anywhere.
- Used a hand-written Java lexer (`StripComments`) rather than regex, so string/char/text-block
  literals (JDBC URLs, `"/swagger-ui/**"`, regexes) are never mistaken for comments. Verified
  idempotent (a second pass changed 0 files) and that the only remaining `/*` occurrences are URL
  paths inside string literals.
- Result: **308 / 543 files changed**, **609 block/Javadoc comments removed**, **967 line comments
  removed**, **40 line comments kept** (why/hazard/deliberate/FIX/NOTE only). Comment-only lines are
  deleted whole; trailing comments are stripped from code; CRLF preserved.
- Verified by the full suite: **623 tests, 0 failures, BUILD SUCCESS**.
- Pre-strip backup of `src/main/java` kept outside the repo (see session notes) so the removed
  comments are recoverable. Tests and `src/main/resources` were deliberately left untouched.
- One file was 100% commented-out dead code — `tenant/repository/ModuleRepository.java` (the live
  one is `rbac/repository/ModuleRepository.java`). Stripping left it 0 bytes, so it was deleted;
  it is unreferenced and compile stayed green. Line endings were preserved (307 CRLF files verified
  against the backup).
