### Gotchas worth not re-deriving

- **Employee usernames are generated**, not what the admin typed (`EmployeeServiceImpl.generateUniqueUsername`;
  e.g. `qa_emp_new` → `qarole1_qaempnew`). Always read `data.username` from the create response —
  logging in with the typed username gives a misleading 401.
- **`createMatter` auto-files the first court case** (`CourtCaseStage.initialFor(level, type)` →
  FILED for civil/district, FIR_REGISTERED for criminal, APPEAL_FILED otherwise). A matter never
  starts with zero court cases; `currentCourtCaseId` points at it.
- **Project-management endpoints take bare DTOs**, not the `{"data": …}` envelope used everywhere
  else, and `PATCH /projects/{code}/status` takes `?status=` as a query param. Case management uses
  the envelope.
- **Role/permission changes bump `permissionVersion` via bulk JPQL**, which bypasses the persistence
  context → a token minted from an already-loaded entity is rejected as stale. Use
  `entityManager.flush(); clear();` before minting (see `QaBaseTest.freshToken`).
- `MeResponse` nests `firm`/`role`, and `RoleInfo` uses `code` (not `roleCode`).
- Global dashboard + audit aggregate with native `date(...)` → H2 (`MODE=PostgreSQL`) can't run it,
  so those two are only smoke-tested (not 5xx). Needs a Postgres pass before release.
- `PermissionEvaluator` caches per user for the TTL (60s in test profile); `QaBaseTest` calls
  `clearAllCache()` after every grant so tests don't read stale permissions.

## Fix batch — findings F-1..F-5, F-7, F-8 (same day, later)

- **F-5** activity endpoint: the `USER_MANAGEMENT:VIEW` check is back on `GET /modules/users/{id}/activity`
  (callers could previously bypass the list/search gate by deep-linking the URL).
- **F-2** portal revocation: `performAuthentication` now refuses a CLIENT whose `portalAccessEnabled` is
  false, and internal `/auth/login` refuses CLIENT accounts outright (they must use the portal route).
- **F-1** suspended firm: blocked at login (`AuthServiceImpl`) **and** on every request in `JwtAuthFilter`
  via the new `FirmRepository.findStatusById`. Per-request, not login-only, because the SA console, the
  trial-expiry scheduler and direct edits all just flip `Firm.status`. *Rejected:* bumping
  `permissionVersion` for all firm users on suspend — clean, but misses the scheduler path.
- **F-4** `GET /api/v1/super-admin/firms` restored in `FirmAdminController`.
- **F-7** create-role dropped `permissionIds`: `FirmRoleServiceImpl.createRoleForFirm` now applies them
  through a new `applyPermissions()` shared with `updateRolePermissions`. Ceiling is caller-aware — SA may
  grant any active non-GLOBAL permission (a firm-admin ceiling would have rejected everything for a
  brand-new firm whose admin still has no perms), firm admin stays capped. Both create surfaces funnel
  here: SA `POST /super-admin/firms/{id}/roles` and firm `POST /firm/roles`.
- **F-3** matter↔client binding: `Matter.clientUserId` + `MatterScopeGuard` + `ReadScopeGuard` +
  `ClientMatterPortalController/Service`, so a CLIENT only ever sees its own matters.
- **F-8** self-service recovery: `/auth/forgot-password` + `/auth/reset-password` — one-time JWT,
  non-enumerable (unknown firm/user returns the same generic outcome), 8–50 policy, revokes live
  sessions on success; plus `password-reset-link/notice` mail templates.

### Two extra defects found and fixed

- **F-15 (High) — tenant privilege escalation via role code.** `createRoleForFirm` accepted any
  `code` and `JwtUtil` grants `ROLE_<roleCode>` straight from it, so a firm admin could create a role
  coded `SUPER_ADMIN`, assign it to an employee, and that employee reached
  `GET /api/v1/super-admin/firms` and `GET /api/v1/admin/roles` (both **200 — reproduced**, not
  theorised). Pre-existing, but inside the function F-7 touched. Guard added (reserved code → 400)
  plus regression test ROLE-06c. **Follow-ups owed:** defence-in-depth in the authority builder, and
  a cleanup for any firm rows already carrying a `SUPER_ADMIN` role.
- **F-8 follow-up — the reset link was not actually one-time** (the javadoc claimed it was): a
  stateless 15-min JWT could be replayed after a successful reset. The token now carries the
  account's `permissionVersion` and redemption compares it against the row — the reset bumps that
  version, retiring the link. Regression assertion added to AUTH-01b.

### Gotcha (new, easy to re-derive)
- Compare `permissionVersion` via the **scalar** `userRepository.findPermissionVersionById`, not
  `user.getPermissionVersion()`: `incrementPermissionVersion` is a bulk JPQL update that bypasses the
  persistence context, so the in-memory entity is stale within the same transaction. Tests exercising
  this need `entityManager.flush(); clear();` — same pattern as `QaBaseTest.freshToken`.

### Reported, not fixed (out of scope)
- `forgotPassword` and `refreshToken` do not consult firm status, so a suspended firm's user can still
  receive a reset link and mint tokens — both are inert (login + filter block them), but inconsistent.
- `GlobalExceptionHandler.handleBadCredentials` overwrites the message, so the "firm suspended" login
  reason never reaches the client (401 is right; the wording is generic).
- `JwtAuthFilter` now does two row reads per authenticated request (permVersion + firm status); they
  could be folded into a single projection.
- `MatterServiceImpl.listMatters`/`getFirmTimeline` degrade to "no client filter" if `isClientScope()`
  is true while `currentUserId()` is null — unreachable today, but fail-open in shape.
- `applyPermissions` rejects duplicate ids in `permissionIds` with a confusing "invalid IDs" message
  (inherited from the update path).
- create-role returns a minimal body that does not echo the permissions it just applied (the SA
  `/admin/roles` upsert does).
