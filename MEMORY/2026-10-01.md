# 2026-10-01

## Document list now embeds a presigned `documentUrl`

- **Reported:** `GET /api/v1/firm/documents?page=0&size=60` returns no URL per row. By design —
  the list was metadata-only and links came from `GET /documents/{id}/download-url`. FE asked for
  a URL inline, so the contract changed: `documentUrl` added to `DocumentResponse`.
- **Keep both paths.** `download-url` stays exactly as-is (and is the only one that writes a
  `DOCUMENT_DOWNLOADED` audit row). The embedded link is a convenience, not a replacement.
- **Populated only for `ACTIVE`** (and only with a storage key). `PENDING_UPLOAD` → null because the
  object may never have arrived; `ARCHIVED` → null because archiving is deliberately not
  downloadable. Done in `DocumentServiceImpl.withDocumentUrl(...)`, applied in both `toResponses`
  (batch list) and the single `toResponse`, so confirm/visibility responses also carry one.
- **Two consequences documented, not fixed:** the embedded URL is a bearer credential with the same
  ~15-min TTL (stale if the page sits open — FE should fall back to `download-url` on click), and a
  download via `documentUrl` is **not audited**. Flagged in the DTO javadoc, the service javadoc and
  `docs/frontend-guide.md` §9/§10. If per-download audit becomes a requirement, the list path needs
  a different mechanism.
- **Tests:** added `DocumentServiceImplTest.ListDocuments` (active → non-null URL containing the
  storage key; pending → null; archived → null). `DocumentServiceImplTest` 39 green,
  `DocumentQaTest` 21 green. No code outside `modules/document` touches the DTO.

## Upload gating — considered removing the assignment check, rejected

- Raised: "any firm member can upload with permission, no admin verification." Correct — `confirm`
  is a *technical* integrity check by the uploader, not a review step; once it passes the doc is
  `ACTIVE` with no sign-off.
- Proposed removing `DocumentScopeGuard.requireUploadAllowed`'s assignment/membership check,
  **rejected by the user**: the per-case assignment rule must stay — assigned staff only can upload
  to a case; non-members cannot. That is exactly what the code already does, so **no change made**.
  (`DocumentScopeGuard` is unmodified.)
- Current enforcement, for the record: `UPLOAD` permission (FIRM_ADMIN + ADVOCATE seeded) **and**
  case-assignment / project-membership for non-admin staff; clients refused outright; firm/super
  admins bypass the assignment check (`isAssignmentScope()` is false for them). Upload, confirm,
  share and archive all route through `requireStaffAction` → same rule.
- Side note for later: a `PRIVATE` document is hidden from **clients** only — colleagues assigned to
  the case can still read it. That was the other candidate change ("hide PRIVATE from other staff"),
  not taken up.

## Super Admin is now refused on every document endpoint

- **Requirement:** documents are firm records; the platform (Super Admin) must not read or touch them.
- **Why the seed alone was not enough:** `PermissionEvaluator.require(...)` returns immediately for a
  Super Admin, so SA bypasses *every* permission check. Removing the `SUPER_ADMIN` grant from the
  `DOCUMENT_MANAGEMENT` matrix would not have blocked them at runtime (and the matrix is
  insert-if-missing, so it would not revoke existing rows anyway).
- **Fix:** `DocumentServiceImpl.requireFirmId()` throws `ForbiddenException` for an SA session. Every
  document operation funnels through it (upload ticket, confirm, all four list paths, download,
  visibility, archive, storage usage), so one check closes the whole surface. No guard/controller
  changes needed.
- **Seed:** `DOCUMENT_MANAGEMENT` matrix SUPER_ADMIN column `FULL → NO_ACCESS` (correct intent for
  fresh DBs + the `/me` permission list); runtime guard is the authoritative enforcement.
- **Tests:** new `DocumentServiceImplTest.SuperAdminAccess` (list/upload/download all 403; list also
  asserts the repo query never runs). 42 green, `DocumentQaTest` 21 green.
- **Docs:** `docs/frontend-guide.md` §8 matrix + scope table now show Super Admin as 403 on every
  document endpoint.

## Storage settings moved into SystemConfig (new STORAGE group)

- **Rule (now written into STATE.md → “Configuration Conventions”):** anything that might change at
  runtime is a config value, not a constant and not yml-only. Add a `ConfigKeyRegistry` entry + a
  `SystemConfigService` runtime helper; the existing `seedGlobalDefaults()` seeds it.
- **Moved to `system_config` under group `STORAGE`:** `STORAGE_MAX_FILE_SIZE_BYTES`,
  `STORAGE_UPLOAD_EXPIRY_SECONDS`, `STORAGE_DOWNLOAD_EXPIRY_SECONDS`, `STORAGE_DEFAULT_QUOTA_BYTES`,
  `DOCUMENT_MAX_FILENAME_LENGTH`.
- **Not moved:** MinIO endpoint/credentials/bucket/region — the `MinioClient` bean is built at
  startup from them (`@ConditionalOnProperty`), and they are environment secrets. The user agreed to
  this split.
- **Behaviour preserved on existing deployments:** the catalog defaults equal the old code values,
  but `seedValueFor` reads the *running* `StorageProperties` for these keys (same trick already used
  for `APP_PRODUCTION`), so a deployment that had tuned `storage.minio.*` keeps its value; absent key
  → yml fallback.
- **Consumers switched:** `DocumentServiceImpl` (max size, upload/download TTLs, filename length),
  `StorageQuotaService` + `StorageUsageBootstrap` (default quota), `DocumentStoragePath` (new
  max-length overloads; safeFilename truncation is caller-supplied). `StorageProperties` now holds
  only connection settings + fallbacks.
- **Tests:** `SystemConfigServiceTest` seed-count 12→17 (inserts 11→16) + new `StoragePolicy` nested
  (yml fallback, stored value wins, seed captures yml); `StorageQuotaServiceTest` and
  `DocumentServiceImplTest` constructors updated to inject `SystemConfigService`;
  `DocumentStoragePathTest` +1 (configurable length). All green:
  SystemConfig 26, StorageQuota 14, DocumentService 42, DocumentStoragePath 10, DocumentQa 21.
- **Docs:** `docs/config-setup.md` GLOBAL key table gained the STORAGE rows.
