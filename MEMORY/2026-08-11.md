## Design review feedback (user's) + the fixes (all implemented + tested today)
1. **Judgment two-path sync (the big one)** — was: `/court-events/{id}/held` with `outcomeType=JUDGMENT_DELIVERED` flipped the case to DECIDED as a side effect WITHOUT judgmentSummary/appealDeadline; the judgment endpoint did it properly. Fix: extracted `CourtCaseService.recordJudgmentInternal(cc, matter, judgmentDate, summary, decisionInFavorOfPartyId)` — THE one place a case becomes DECIDED. `markHeld` now REQUIRES `judgmentDate` + `judgmentSummary` inline when outcomeType=JUDGMENT_DELIVERED (400 otherwise) and delegates. The two paths can never drift.
2. **REVIEW vs closed-parent guard** — REVIEW is now exempt from the "cannot attach to a closed parent" rule (a review petition comes AFTER the judgment is final) and the parent is left untouched (not marked APPEALED). `MatterService.addCourtCase`.
3. **PartyType** — added `COMPLAINANT`, `INFORMANT` (the state/complainant side opposite `ACCUSED`).
4. **Leave-to-appeal decision** — High→Supreme is a leave-petition process, not an automatic appeal. Added `AppealDeadlineRule.requiresLeave` (seeded true for the 3 High rows) and `CourtCase.appealRequiresLeave` (set true when judgment recorded on a HIGH case, surfaced in `CourtCaseResponse`/`UpcomingAppealResponse`). Deadline numbers unchanged (35/70 days). **Note: new columns must be `Boolean` wrapper, NOT primitive** — legacy rows carry NULL and a primitive breaks Hibernate hydration (this bit us: `Null value was assigned to property requiresLeave` — fixed by switching to `Boolean` + `Boolean.TRUE.equals(...)`).
5. **Allowed-stages endpoint** — `GET /court-cases/{ourCourtCaseRef}/allowed-stages` returns legal next moves (transitions filtered by level/type/relation) so the frontend never duplicates the state machine.
6. **Smaller**: `partyIsState` removed from `RecordJudgmentRequest` (recorded once at court-case creation; engine trusts the stored value); **appeal-deadline watch** `GET /court-cases/appeal-deadlines?withinDays=30` (decided, not-lapsed, no appeal filed); **conflict policy** — PESHI overlaps hard-block (400), TARIK overlaps are allowed with `conflictWarning` on `CourtEventResponse`.
