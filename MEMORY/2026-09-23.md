## QA fix batch — six reported bugs

Six bugs off `docs/ui-test-checklist.md` plus the client-portal login report, all fixed in one
sitting. Full per-bug write-up (symptom → root cause → change → manual steps) is in `fixes.md` at
the repo root. **461 tests green** (was 423 recorded), `BUILD SUCCESS`.

Run (the shell's default `JAVA_HOME` is JDK 17 and cannot build this module):
`JAVA_HOME=/c/Users/Dev/.jdks/ms-21.0.12 ./mvnw -o test`

1. **Client portal could not log in (1.12).** `login` resolved a client by *mobile number only*
   while the portal's single, username-labelled field is what clients type. Added
   `findClientAccount()` (mobile → then username) and added the mobile arm to `forgotPassword`.
   Regression test `AUTH-09b` creates a client and signs in with both identifiers.
2. **Reset / change password (1.8, 1.9).** Three defects at once: (a) the admin reset endpoint
   required `ApiRequest<ResetPasswordRequest>` with a mandatory password, but the console's reset is
   a confirmation dialog that posts **no body** → 400 before the controller; (b) the reset accepted
   `aaaaaa` because client creation allowed 6 characters and the resets 8; (c) no self-service
   "change my own password" existed. Fixes: a new `RequestBodyBinder` (envelope or bare body,
   body optional), a new `PasswordPolicy` (8–50) used by both resets, client creation and the new
   endpoint, a generated temporary password returned once when the admin supplies none, and a new
   `POST /api/v1/me/change-password` that proves the current password and revokes other sessions.
3. **`isTrial` (2.8).** Added `isTrial` / `trialDays` / `trialExpiresAt` to `FirmAdminResponse` and
   `FirmProfileResponse`; populated in the two service builders. `FirmMapper`'s duplicate (and
   uncalled) builders were left alone — flagged for deletion in `fixes.md`.
4. **Bulk deactivate (4.10).** Same binding bug as 2.1 — the screen posts `{"userIds": […]}` bare.
   Both bulk endpoints now bind through `RequestBodyBinder`, and an empty selection is rejected in
   the service (the envelope's `@Valid` never covered these paths).
5. **Assignment e-mail (5.7).** `CASE_ASSIGNED` *was* published, but e-mail defaulted on for ALERT
   types only, so a SYSTEM assignment only produced an in-app row. `NotificationType` now declares
   `emailsByDefault` per type; `CASE_ASSIGNED` is the one SYSTEM type that declares true and stays
   overridable.
6. **Unassigned employee saw every matter.** `GET /firm/matters` only narrowed for clients; every
   other non-admin fell through to the firm-wide query (the dashboard already scoped by assignment).
   Added `ReadScopeGuard.isAssignmentScope()`, routed the matter and stale-matter lists through a
   new `assignedMatters()` (empty page when the caller has none) and a
   `MatterRepository.findByFiltersAndIdIn(...)` that keeps all existing filters.

### Gotchas learned

- **No converter is registered for `JsonNode` request bodies** in this app's web layer, so binding
  `@RequestBody JsonNode body` fails with `Type definition error: [simple type, class
  com.fasterxml.jackson.databind.JsonNode]` and surfaces as the 400 the whole batch was meant to
  fix. Take the body as `String` and parse it with the `ObjectMapper` (`RequestBodyBinder` does).
- `./mvnw` picks up `JAVA_HOME=…ms-17.0.20` from the environment; pass the JDK 21 path explicitly.
- Test counts: full suite 461; the QA suites are 63 (`AuthSecurityQaTest` 16, `SuperAdminQaTest` 16,
  `FirmRoleMatrixQaTest` 12, `CaseManagementQaTest` 11, `ProjectManagementQaTest` 8).

## Follow-up: forgot-password e-mail dead + admin-typed reset password "doesn't take"

Full write-up appended to `fixes.md` (sections F1/F2). **462 tests green** (`AUTH-14` added).

- **E-mail root cause was a corrupted yml line**, not the flow: `spring.mail.username` read
  `${MAIL_USER:tryaac1ss@gmail.com} to d` — placeholder resolution keeps trailing text, so SMTP
  authenticated as `tryaac1ss@gmail.com to d` (535) and the From fallback got the same illegal
  address. App password also had Gmail's display spaces in it. Fixed both; `resolveFromAddress`
  now only uses the username when it looks like an address; `resolveMailSender` logs its chosen
  source at INFO. **Verified auth-only against smtp.gmail.com:587 → `235 2.7.0 Accepted`** (no
  mail sent). Failures stay invisible by design (`sendHtmlEmail` swallows, forgot-password is
  generic), so `EMAIL_FAILED:` log lines remain the place to look.
- **Admin reset flow, as built:** dialog posts no body → service generates a temp password,
  returns it ONCE in `data.temporaryPassword`, forces rotation, notice e-mail carries nothing —
  and the dialog never displays the response field, so nobody ever sees the password. An
  admin-chosen password works only under the key `newPassword`.
- **Backend fix:** `@JsonAlias({"password","pwd","new_password"})` on `ResetPasswordRequest` so
  a differently-named field can't be silently dropped into "generate"; `@Operation` docs on both
  reset endpoints now spell out both shapes. No-body path unchanged. Frontend (separate repo,
  not accessible) still owes: a password field posting `{"newPassword": …}` + rendering
  `generated`/`temporaryPassword`.
- **Test/infra gotchas this round:**
  - The build JDK on this machine is `JAVA_HOME="$HOME/.jdks/corretto-21.0.11" ./mvnw -o test` —
    the previously recorded `/c/Users/Dev/.jdks/ms-21.0.12` does not exist here (user dir is
    `tryaa`; env default is JDK 25, module needs 21).
  - `MockHttpServletRequestBuilder` has no `.andReturn()` — build with it, then
    `mockMvc.perform(builder).andReturn()`.
  - SMTP creds can be checked without sending anything: pipe `EHLO`/`AUTH PLAIN` through
    `openssl s_client -starttls smtp`, with sleeps — data written before the handshake finishes
    yields `451 SMTP protocol violation`.

## F-9 closed: refresh revocation + server-side logout

Full write-up in `fixes.md` §F9; QA table row struck in `docs/qa-report-2026-09-21.md`.
**466 tests green** (AUTH-15..18 added, watched red first).

- **New `refresh_tokens` store** (`auth/entity/RefreshToken`, keyed by the JWT `jti`):
  rotation marks the row used and mints a fresh token; replaying a used one revokes the
  account's whole family. Revoke is an entity write, NOT a bulk `UPDATE` — bulk bypasses the
  persistence context, which then serves a stale "active" sibling (this is the same staleness
  class as `incrementPermissionVersion`, already documented in `resetPasswordWithToken`).
- **Refresh tokens carry `permVersion`** and `refreshToken()` checks it → password resets, role
  changes and logout retire them. Proved a real unreported hole: before the fix an admin reset
  left live refresh tokens minting fresh access tokens (AUTH-17 red run: 200).
- **`POST /api/v1/auth/logout`** (new, authenticated, no body): bumps `permissionVersion` → all
  access tokens refused by the filter immediately, all refresh tokens refused at refresh — every
  device. Uses the pre-existing `AuditAction.LOGOUT`.
- **`JwtAuthFilter`**: removed the `!"SUPER_ADMIN"` exemption — SA sessions obey staleness too.
- **Gotcha:** `refreshToken()` must stay **non-`@Transactional`** — the family revoke sits right
  before a thrown exception and an outer transaction rolled it back (AUTH-15 failed on exactly
  this). Ops commit individually; all failure paths are fail-closed.
- New files: `RefreshToken`, `RefreshTokenRepository`. Touched: `JwtUtil` (jti + permVersion claim
  + `extractTokenId`/`getRefreshExpiryMs`), `AuthServiceImpl`, `AuthService`, `AuthController`,
  `AuthConstants`, `JwtAuthFilter`, `SuperAdminServiceImpl` (records SA refresh rows too),
  `SuperAdminServiceTest` (+`@Mock RefreshTokenRepository`).
