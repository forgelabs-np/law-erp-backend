Notification Module

In-app notifications for the portal — the bell icon: a per-user feed, an unread badge, and read-state management, driven by an in-process event pipeline that domain modules publish into.

1. Overview & Architecture

Domain modules (casemanagement, invoice, …)
    │  publish NotificationEvent via ApplicationEventPublisher
    ▼
NotificationEventListener          @Async("taskExecutor") — separate bean so the
    │                              proxy applies; exceptions swallowed, never
    │                              break the producer's business flow
    ▼
NotificationOrchestrator           resolves recipients (direct user / role
    │                              fan-out / all firm users — always firm-scoped),
    │                              dedup check, renders copy, persists rows
    ▼
notifications table                one row per recipient
    ▼
REST API                           list / unread-count / mark-read / mark-all-read

Deliberate v1 scope (Phase 2 triggers in brackets):

  • Polling only — frontend polls unread-count every 45–60s. No WebSocket/SSE. [Phase 2: SSE push if users demand real-time]
  • In-app channel only — no email/SMS dispatch, no notification_delivery table. [Phase 2: email channel — the delivery table + retry sweep earn their place when a channel can fail]
  • Code-level rendering — NotificationRenderer, no DB templates. [Phase 2: DB templates when Nepali/English i18n lands]
  • No user preferences. [Phase 2: notification_preference + toggle UI]
  • Taxonomy SYSTEM | ALERT | BROADCAST is final; TRANSACTIONAL (password reset, MFA) intentionally excluded — those are request-response flows owned by EmailService.

Swapping the in-process bus for a broker later means replacing NotificationEventListener — producers never change.

2. Data Model

notifications

Column Type Notes
id UUID PK (AuditableEntity)
uuid UUID unique secondary id
firm_id UUID NOT NULL tenant scope — enforced in every query path
recipient_user_id UUID NOT NULL one row per recipient (fan-out at write time)
type VARCHAR(40) NOT NULL enum NotificationType
category VARCHAR(20) NOT NULL enum NotificationCategory (pinned from type)
title VARCHAR(200) NOT NULL rendered copy
body TEXT NOT NULL rendered copy
reference_type VARCHAR(40) polymorphic link: MATTER, INVOICE, …
reference_id UUID id of the referenced entity
read_at TIMESTAMP NULL = unread
dedup_key VARCHAR(200) optional idempotency key
created_at / created_by / updated_at / updated_by — from AuditableEntity

Indexes: (recipient_user_id, read_at) — the hot path; (firm_id); unique (dedup_key, recipient_user_id) — per-recipient idempotency (multiple NULL keys coexist).

Enums

  • NotificationCategory: SYSTEM, ALERT, BROADCAST
  • NotificationType: CASE_ASSIGNED, INVOICE_STATUS (live) · HEARING_REMINDER, APPEAL_DEADLINE, ANNOUNCEMENT (Phase-2 placeholders, no producers, renderer rejects them loudly)

3. API Reference

Base: /api/v1/notifications — all endpoints act on the JWT-authenticated user; no user id is ever accepted from the client.

GET /api/v1/notifications?unreadOnly=false&page=0&size=20

Paged feed, newest first. size clamped to 1–100.

{
  "status": "SUCCESS",
  "message": "Notifications fetched successfully",
  "data": {
    "content": [
      {
        "id": "…",
        "type": "CASE_ASSIGNED",
        "category": "SYSTEM",
        "title": "Assigned to matter",
        "body": "You were assigned to matter APX-MAT-2026-00042 as PRIMARY_ADVOCATE.",
        "referenceType": "MATTER",
        "referenceId": "…",
        "read": false,
        "readAt": null,
        "createdAt": "2026-09-09T12:00:00"
      }
    ],
    "page": 0, "size": 20, "totalElements": 1, "totalPages": 1,
    "first": true, "last": true, "empty": false
  }
}

GET /api/v1/notifications/unread-count

Lightweight badge endpoint for 45–60s polling.

{ "status": "SUCCESS", "message": "Unread count fetched successfully", "data": { "count": 3 } }

POST /api/v1/notifications/{notificationId}/read

Stamps read_at; idempotent (re-marking is a no-op). 404 if the notification doesn't exist, 403 if it belongs to another user.

POST /api/v1/notifications/read-all

Marks every unread row for the current user. Returns { "updated": <n> }.

4. Producing Notifications (for backend devs)

Domain modules publish; they never touch persistence or channels.

// Direct recipient
eventPublisher.publishEvent(NotificationEvent.toUser(
        firmId, assigneeUserId, NotificationType.CASE_ASSIGNED,
        "MATTER", matter.getId(),
        Map.of("matterNumber", matterNumber, "assignmentRole", role.name())));

// Role fan-out within the firm (resolved via userRepository.findUserIdsByFirmIdAndRoleCode)
eventPublisher.publishEvent(NotificationEvent.toRole(
        firmId, RoleCode.FIRM_ADMIN, NotificationType.INVOICE_STATUS,
        "INVOICE", invoice.getId(),
        Map.of("invoiceNumber", invoiceNumber, "status", newStatus.name())));

Rules:

  • Exactly one targeting mode per event (recipientUserId | recipientRoleCode | allFirmUsers=true) — otherwise the orchestrator throws.
  • Set dedupKey when the same logical event can fire twice (schedulers, retries). Convention: TYPE:REFERENCE:id:userId[:bucket].
  • Adding a new type: extend NotificationType (pin its category), add a renderer branch, add copy constants to NotificationConstants, write the producer test. The renderer's exhaustive switch makes a missing branch a compile/test failure, not a runtime surprise.

Live producers:

Producer Event Recipients
CaseAssignmentServiceImpl.assign CASE_ASSIGNED the assigned user
InvoiceServiceImpl.updateStatus INVOICE_STATUS all FIRM_ADMIN users of the invoice's firm

5. Security & Multi-Tenancy

  • Every endpoint resolves the user from the JWT (CurrentUserResolver); unauthenticated → 401.
  • Mark-read checks ownership: a notification whose recipient_user_id differs from the caller → 403. Combined with firm_id on every row, cross-user and cross-firm access are both impossible.
  • Role fan-out queries are firm-scoped by construction (firmId + roleCode) — no notification can leak across firms.
  • No new security-config entries needed: /api/v1/notifications/** falls under anyRequest().authenticated().

6. Frontend Integration Guide

  1. Badge — poll GET /unread-count every 45–60s while logged in; show data.count on the bell. Refresh immediately after any mark-read call.
  2. Panel — on bell click, GET /notifications?page=0&size=20; paginate with page/totalPages. Optionally unreadOnly=true for an "unread" tab.
  3. Click-through — map referenceType → route client-side (e.g. MATTER → /matters/{referenceId}, INVOICE → /invoices/{referenceId}). On click: POST /{id}/read, then navigate. Unread rows render with a dot/bold; read/readAt drive styling.
  4. Mark all — button calls POST /read-all, then re-fetches the list and zeroes the badge.
  5. Category → icon/color mapping: SYSTEM (info), ALERT (warning), BROADCAST (announcement).
