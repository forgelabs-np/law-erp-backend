## 3. New findings

> **Status, same day: NEW-1, NEW-2 and NEW-3 are fixed and re-verified live — see §7.** The findings
> below are kept as written (they describe the state that was measured); §7 records the fixes, the live
> re-run and the one new recovery endpoint.

### NEW-1 (High) — Login lockout is non-functional, so passwords can be brute-forced

`/api/v1/auth/login` never persists failed attempts. Five consecutive wrong passwords left
`login_attempts = 0` and `locked_until = NULL`.

**Root cause:** `AuthServiceImpl.authenticateInternalUser` / `authenticateClient` are `@Transactional`.
`handleFailedLogin()` bumps the counter and saves, then throws `BadCredentialsException` (a
RuntimeException), so Spring rolls the transaction back and the increment is discarded. The same
rollback also drops the `LOGIN_FAILED` login-history and audit rows for that attempt.

**Why the suite says it passes:** `E2eSecurityConfigProbeTest` is annotated `@Transactional`
(line 26), so its `loginLockoutHonoursDbConfiguredMaxAttempts` assertion reads the increment from the
shared, uncommitted persistence context. In production each request gets its own transaction and the
increment disappears. **This is a false green** — the test cannot catch the bug it exists to catch.

### NEW-2 (High) — `/super-admin/login` never locks the account

With `LOGIN_MAX_ATTEMPTS=1`, two wrong super-admin passwords left `login_attempts = 2` and
`locked_until = NULL`. This path is **not** `@Transactional` (which is why the counter persists here),
but the password-failure branch never calls `setLockedUntil` — only the MFA branch
(`registerFailedMfaAttempt`) does. So the platform's most privileged account can also be brute-forced.

### NEW-3 (High) — A firm admin cannot use its own firm config

`GET/PUT /api/v1/firm/config` returns **403** for firm admin `tlaw`. The `FIRM_CONFIG:*` permissions
exist only on the **global template** roles (`firm_id IS NULL`); TLAW's cloned `FIRM_ADMIN` role has 73
permissions and **none** of the four `FIRM_CONFIG` ones. So firm branding, email footer and timezone
are unusable by the role that is supposed to own them. (Same class as QA finding F-12: firm role clones
are not back-filled when new permissions are introduced.)

### NEW-4 (Medium) — `MFA_ENABLED=N` does not stop MFA for existing users

Confirmed live: with the global key off, the existing super admin still received an `mfaToken`. Login
challenges on the per-user `mfaEnabled` flag. This is the F-2 behaviour, now proven against the DB.

### NEW-5 (Medium) — The committed encryption key decrypts MFA secrets

Using only `config.encryption.key` from the repo's `application.yml`, both users'
`mfa_secret` values were decrypted and valid TOTP codes generated (T7 then logged in with one). Anyone
with the repo plus a DB read can mint valid second factors.

### NEW-6 (Info) — A plaintext MFA secret self-heals

`superadmin.mfa_secret` was 32-char plaintext at the start of this session and is now 80-char
ciphertext: the entity converter re-encrypts on the next save (a successful login saves the user). The
boot-time `AES decryption failed` error only appears until that first save.

- Can read/write any firm's config. Auth and MFA work; the real TOTP path is verified.
- **Broken for this role:** its own lockout never engages (NEW-2).

  logo-adjacent branding work shipped on 2026-10-07/08 are unreachable for the exact role meant to use
  them. This is the most user-visible defect found: the product's white-labelling is dead on arrival
  for an existing firm.

### Employee (FIRM_USER / ADVOCATE, 30 permissions)

- Clean: login without MFA, `/me` works, every admin surface returns 403.
- No defect found for this role in this pass. It is the role the isolation model protects best.

### Client

- The `CLIENT` role has **0 permissions** (as designed — the portal does not use RBAC).
- Wrong-door guards work: an employee hitting the client login endpoint is refused with a real reason.
- **Not verified:** no client fixture exists in this database, so the portal's own journey (first-login
  rotation, matter visibility, document access) could not be exercised. This remains coverage debt —

### 7.3 How to release a locked account (no database access needed)

A lock is automatic and temporary: `LOGIN_MAX_ATTEMPTS` (seeded `5`) failures stamp
`locked_until = now + LOGIN_LOCK_MINUTES` (seeded `30`), so **waiting `LOGIN_LOCK_MINUTES` clears it by
itself**. To release it immediately, use the new endpoints as an admin:

```bash
# Super admin — any user in any firm
curl -X POST "$BASE/api/v1/super-admin/users/<userId>/unlock" -H "Authorization: Bearer <SA_TOKEN>"

# Firm admin — only users of its own firm
curl -X POST "$BASE/api/v1/modules/users/<userId>/unlock" -H "Authorization: Bearer <FIRM_ADMIN_TOKEN>"
```

Both clear `login_attempts` and `locked_until` and write a `USER_UNBLOCKED` audit row. They deliberately
do **not** touch the password, MFA or the blocked/active flags. Equivalent pre-existing paths: an admin
password reset (also clears the lock) or a self-service reset + rotation.

**Full recovery matrix** — lockout vs blocked vs deactivated vs suspended firm, API first and SQL
last: **`docs/account-recovery-runbook.md`**.

**Caveat, verified live:** a locked **sole** super admin cannot mint the token needed to call its own
unlock endpoint — the login that would issue it is the locked one. It can still be released by an
already-issued, unexpired SA token (tested: 200 and reset), or by waiting out the lock, or by an operator
with database access. Worth a documented break-glass procedure.
