## 1. Why this pass existed

The existing integration and QA suites are broad, but they mostly **mint JWTs directly** and **set up
modules / role grants by writing the database**, so three real flows were never exercised end to end:

1. register super admin → MFA setup → confirm → access token
2. firm admin first login → forced password rotation → MFA setup → access token
3. employee / client first login → forced rotation → access token

That blind spot is exactly where the defects below were hiding. The new `FullLifecycleE2ETest` obtains
**every token from a real login** and drives the whole journey through the public API.

## 3. The full-lifecycle journey (`FullLifecycleE2ETest`)

Single test, `@Transactional` (rolled back), MinIO replaced by an in-memory `FakeStorageService`.
Every token comes from a real login.

| Step | Action | Asserted result |
|---|---|---|
| 1 | `POST /super-admin/register` with the registration secret | 200, returns `userId` |
| 2 | `POST /super-admin/login` then MFA confirm (`/auth/mfa/setup/confirm`, dev code `123456`) | `MFA_SETUP_REQUIRED` + QR URI → access token |
| 3 | `POST /super-admin/firms` | firm created, admin created with `mustChangePassword=true` |
| 4 | `POST /super-admin/firms/{id}/modules` for every module | each enable returns 200 |
| 5 | `PUT /super-admin/firms/{id}/roles/{roleId}/permissions` | FIRM_ADMIN granted all permissions |
| 6 | Firm admin first login → `POST /auth/change-password` → MFA setup | `PASSWORD_CHANGE_REQUIRED` → `MFA_SETUP_REQUIRED` → token |
| 7 | Firm admin re-login with rotated password | `MFA_REQUIRED` → validate → token |
| 8 | Firm admin reads `/firm/profile`, `/firm/modules`, `/firm/roles`, `/modules/users` | 200 each |
| 9 | Firm admin grants ADVOCATE role a working permission set | 200 |
| 10 | `POST /firm/employees` | 200, generated username returned |
| 11 | Employee first login → forced rotation | `PASSWORD_CHANGE_REQUIRED` → token (no MFA for ADVOCATE) |
| 12 | Employee uses `/me`, `/firm/dashboard`, `/firm/calendar/today`, `/firm/matters`, creates a matter | 200 each; `/me` exposes enabled modules |
| 13 | Employee denied admin surfaces (`/firm/employees`, `/firm/roles`) | 403 |
| 14 | Firm admin assigns the employee to the matter | employee now sees the assigned matter in their scoped list |
| 15 | Document upload (`POST /firm/documents`, multipart) on the matter | `ACTIVE`, correct `matterNumber` |
| 16 | Firm admin creates a client + a client project | 200 |
| 17 | Client portal login (`/auth/client/login`) → `/me`, `/client/matters`, `/client/projects` | token issued, own data only |
| 18 | Super admin still sees the firm (`/super-admin/firms`, `.../admins`, `.../roles`, `/super-admin/users`) | 200 each |

**A design note confirmed, not a bug:** employees derive navigation from `GET /me`
(`MeResponse.modules`), and `/firm/modules` is deliberately `FIRM_ADMIN`-only. The first run failed
because the test asserted the wrong endpoint; the app was correct.

## 4. Defects found and fixed

### D1 — A second super admin could be registered (HIGH)
- **Symptom:** `POST /super-admin/register` succeeded (200) for a second admin with a different
  username/email/mobile, contradicting the app's own "Only one super admin allowed."
- **Cause:** `/super-admin/register` guarded by `existsByUsernameAndUserType(username, SUPER_ADMIN)`
  — a per-username check, not a singleton check.
- **Fix:** `countByUserType(SUPER_ADMIN) > 0` → 400.
- **Evidence:** `E2eSecurityConfigProbeTest.onlyOneSuperAdminMayRegister` — failed (200) before, passes after.

### D2 — Login-lockout settings were dead config (HIGH)
- **Symptom:** `LOGIN_MAX_ATTEMPTS` / `LOGIN_LOCK_MINUTES` in the admin Settings UI had no effect.
- **Cause:** `SystemConfigService.loginMaxAttempts()` / `loginLockMinutes()` were **never called**;
  `AuthServiceImpl` read `@Value("${security.max-login-attempts:5}")` (a key absent from every yml →
  always 5) and hardcoded a 30-minute lock. Direct violation of the project's "runtime values live in
  `system_config`" rule.
- **Fix:** both values now read from `SystemConfigService`.
- **Evidence:** `loginLockoutHonoursDbConfiguredMaxAttempts` — with `LOGIN_MAX_ATTEMPTS=1` the account
  now locks after one failure (asserted on the DB row, because of D5).

### D3 — First-login password-change token was replayable (MEDIUM)
- **Symptom:** the same `passwordChangeToken` changed the password a second time within its 10-minute
  life.
- **Cause:** `/auth/change-password` accepted any valid `pwd_change` token regardless of
  `mustChangePassword` (and the token carries no version/one-time marker).
- **Fix:** reject once `mustChangePassword` is false (single-use).
- **Evidence:** `passwordChangeTokenIsSingleUse` — replay returned 200 before, 401 after.

### D4 — Document upload failed on PostgreSQL: unapplied migration (reported live)
- **Symptom:** `INSERT into matter_timeline (... event_type='DOCUMENT_UPLOADED')` → SQLState `23514`,
  violates `matter_timeline_event_type_check`.
- **Cause:** `db/migration/V2026_09_28__document_store_constraints.sql` was **never applied** to the
  Supabase dev DB. Hibernate `ddl-auto=update` creates enum CHECK constraints only when it creates a
  table and never alters an existing one.
- **Fix:** applied the migration over JDBC (idempotent). Constraint went **13 → 14 values** (added
  `DOCUMENT_UPLOADED`); `documents_owner_xor_check` was added too. Verified by printing
  `pg_get_constraintdef` before/after and a rolled-back `DOCUMENT_UPLOADED` insert now accepted.
- **Not caused by the auth fixes** — my code changes were auth-only.

### D5 — Orphaned object left in storage on a post-upload failure (MEDIUM)
- **Symptom:** when the timeline insert failed, the DB rows rolled back but the uploaded bytes stayed
  in the bucket, uncounted by the quota.
- **Cause:** `DocumentServiceImpl.upload` discarded the object for size/type/quota failures but the
  final `save` + `recordTimeline` + `toResponse` block was unguarded, despite a comment promising
  cleanup.
- **Fix:** wrap that block in try/catch → `discard(storageKey)`.
- **Evidence:** `DocumentServiceImplTest.discardsWhenTimelinePersistenceFails`.

## 5. Defects found, deliberately not changed (need a product decision)

### D6 — All login errors collapse to one generic message (LOW) — **FIXED 2026-10-07**
`GlobalExceptionHandler.handleBadCredentials` returned "Invalid username or password" for **every**
`BadCredentialsException`, so "Account locked", "account inactive", "firm suspended" and "portal
access disabled" were never shown. The handler now surfaces the message, and
`AuthServiceImpl.performAuthentication` was reordered so the password is proved **before** any
account-state reason is named — otherwise every one of those checks becomes an unauthenticated
username/account-type oracle. `AuthenticationManager` gave way to `passwordEncoder.matches` because
`DaoAuthenticationProvider` refuses a disabled/locked account before it compares the password.
(D2's probe still asserts on the DB row; FINDING-4a locks the surfaced wording.)

### D7 — Clients are never forced to rotate the admin-set password (MEDIUM) — **FIXED 2026-10-07**
`ClientServiceImpl.createClient` did not set `mustChangePassword`, so a client kept the password the
firm admin chose forever, while FIRM_ADMIN and employees were forced to rotate. It now sets it, so
the first portal sign-in returns `PASSWORD_CHANGE_REQUIRED` like an employee's first login.

## 9. Enhancement suggestions

1. **Replace level-based auth endpoints with a state machine** (`/auth/login` → `nextStep`): the three
   login shapes (password change / MFA setup / MFA required / success) are currently inferred from a
   `status` string by the client. A single `nextStep` enum + `nextEndpoint` field removes guesswork.
2. **Make the E2E run against PostgreSQL in CI.** The D4 class of bug (stale CHECK constraint) is
   invisible on H2. A Testcontainers Postgres profile would have caught it at build time; the new
   `MigrationConstraintDriftTest` is a cheaper stopgap.
3. **Automate migrations.** The project has no Flyway/Liquibase and relies on someone running SQL by
   hand — the direct cause of D4. Adopting Flyway (or a tiny startup reconciler for enum CHECKs) would
   make "add an enum value" self-consistent.
4. **Self-cleaning uploads.** Prefer a transaction-synchronization callback (delete the object on
   rollback) over the local try/catch, so any future failure after `storage.put` is covered, not just
   the paths known today.
5. **Login-audit clarity.** With D6 pending, log the real reason server-side (already partly done) and
   surface a non-enumerating generic message plus a support code the user can quote.
6. **Contract tests for the FE journey.** Pin the exact `LoginResponse` shapes per status and the
   `/me` module payload, so a backend change can't silently break the frontend's login/MFA screens.
7. **Broaden the E2E to failure paths:** firm suspended mid-session, role downgrade invalidates the old
   token, quota exceeded on upload, and cross-firm IDOR attempts inside the same journey.
