Scraper Module — Nepal Supreme Court Hearing Tracking

daily + weekly cause lists → normalize → store → match → notify → weekly CSV snapshot
com.lawfirm.erp.modules.scraper · Spring Boot 4 · jsoup + java.net.http

1. What the module does

Every weekday the module pulls the entire cause list of each court where we have an active client case, stores it, then matches our registered cases against it and notifies. Every Monday it also pulls the weekly (Sun–Fri) list, and exports the previous completed week to a CSV file as an offline snapshot. The DB is the system of record; the CSV is a convenience copy — nothing is ever deleted.

How one court is scraped

  1. GET the endpoint first — the server issues PHPSESSID, court_session (which binds the User-Agent, so a fixed browser UA is sent) and an F5 TS… cookie.
  2. POST the form: daily = todays_date (Arabic BS) + pesi_date (Devanagari BS) + submit; weekly = pesi_bar=all + submit.
  3. The server answers 302 with a flash message in the cookie; we follow Location with a GET to receive the final page.
  4. Parse the page with the two dedicated parsers, normalize, and upsert.

All numerals on the site are Devanagari (०८१-C४-३८२७) — converted to Arabic on ingest. Dates are Bikram Sambat; both the BS string and the converted AD date are stored (NepaliDateUtil, verified: 2083-05-01 = 2026-08-17). Every row carries both case-number forms: the court-visible caseNoBs (081-C4-3827) and the court-scoped caseNoInternal (39-081-32030 — the parenthesized form, which is what matching uses).

Not published? If the site has no list for a date (common early morning), the scrape returns 0 rows, nothing is stored for that date, and an alert is logged. This is expected behaviour, not an error.

3. Storage (PostgreSQL, auto-created)

TableContentsKey / notes
scraper_courtsCourt registry (39 = Kathmandu, 63 = Gulmi)courtId PK, matches the site URL segment
scraper_client_casesYour cases: courtId + caseNoInternal + statusACTIVE rows drive which courts are scraped
scraper_daily_hearingsNormalized daily rows (has outcome column)numeric id · bench (इजलाश) + serial (क्र. स.) · unique (courtId, caseNoInternal, hearingDateBs) → idempotent upsert
scraper_weekly_hearingsNormalized weekly rows (no outcome column, no benches)numeric id · serial (क्र. स.), bench always null · same unique key
scraper_hearing_matchesThe app's working set: your case × hearing, with full detailnumeric id · unique per (clientCaseId, courtId, hearingDateBs); notified flag

All scraper tables use numeric auto-increment ids (no UUID) and carry a scrapedDate column (when the row was pulled) — no audit columns. Rows store the bench (इजलाश) the case was listed before (daily feed only) and its serial (क्र. स.) within the bench/date group (Devanagari digits normalized to Arabic; letters like क stay as-is).

Matching

After every ingest, HearingMatchingService joins client_cases × hearings on (courtId, caseNoInternal) for today/upcoming hearings. New matches are inserted into hearing_matches (deduped — re-runs skip existing), copying the full row (subject, plaintiff, defendant, caseNoBs, judge, order type) so matches are self-contained. Legacy matches created before the detail columns existed are backfilled automatically on startup.

Notification

New matches go through the NotificationDispatcher interface — currently the log stub ([scraper-notify:log] …). Delivery is at-least-once: a match is marked notified only after a successful dispatch, so a broken channel never loses a match and never blocks matching.

4. Services — what each class does

The module is a small pipeline of focused classes. Each has one job and a narrow seam, so the scrape path, the matching path and the notification path stay independent.

HTTP client — CourtSiteClient (interface) / HttpCourtSiteClient

  • Only class that talks to supremecourt.gov.np. One method per feed: scrapeDaily(courtId, dateBs) and scrapeWeekly(courtId).
  • Session flow per call: GET (cookie handshake) → POST form → follow the 302 Location with a GET. Sends a fixed browser User-Agent (the session binds it) and respects request-delay-ms between requests.
  • Interface first so a Selenium/Playwright impl can be swapped in later without touching the rest of the pipeline.

Converters

  • DevanagariConverter — ०-९ ↔ 0-9, used on every parsed field and on the outgoing pesi_date form value.
  • NepaliDateUtil — BS ↔ AD with the 2000–2090 month-length table (epoch BS 2000-01-01 = AD 1943-04-13). Verified against 2081-01-01 → 2024-04-13 and 2083-05-01 → 2026-08-17.
  • CaseNumberExtractor — pulls both forms from one cell: the court-visible caseNoBs (081-C4-3827) and the parenthesized court-scoped caseNoInternal (39-081-32030).

Parsers — one per table structure, same output

  • DailyTableParser — real daily page: skips the judge-count summary table, reads the page date from the मिति … को title, walks per-bench sections (bench header table → record_display detail table). Extracts bench (इजलाश number) + judge (from td.judge), serial (क्र. स.), both case numbers, parties, subject and the आदेश फैसलाको किसिम outcome column.
  • WeeklyTableParser — real weekly page: grouped by पेशी मिति :<date>, flat 9-column table per date, combined पक्ष ‖ विपक्ष split on ‖/||. No bench, no judge, no outcome — those fields stay null.
  • Both emit the same normalized HearingRecord DTO, so ingestion never knows which feed a row came from.

Orchestrator — ScraperService

  • getActiveCourts() — distinct courtIds from client_cases where status = ACTIVE (dynamic, never hardcoded).
  • runDailyScrape(dateBs) / runWeeklyScrape() — fan out one scrape per active court on a bounded executor (max-concurrent-courts), collect per-court results, then matchAndNotify(). Alerts ([scraper-alert]) on failure or 0 rows; a failing court never stops the others or the matching step.
  • runDailyScrapeForCourt(courtId, dateBs) / runWeeklyScrapeForCourt(courtId) — single-court entry points behind the admin endpoint.
  • getHearingStatus(caseNoInternal, dateBs) — read path: our DB only, no live scrape. Optional BS date filters to that day's list.

Ingestion — HearingIngestionService

  • Idempotent upsert keyed on (courtId, caseNoInternal, hearingDateBs) — re-scraping the same day replaces in place, never duplicates.
  • Copies the full normalized row (bench, serial, judge, parties, subject, order type) and stamps scrapedDate.

Matching — HearingMatchingService

  • Joins active client cases × ingested hearings on (courtId, caseNoInternal) for today/upcoming; inserts new rows into hearing_matches, copying the full row so matches are self-contained.
  • Deduped on (clientCaseId, courtId, hearingDateBs); backfillLegacyMatches() enriches pre-detail rows at startup.
  • Independent of the scrape — reads whatever is already ingested, so a slow/failed scrape never blocks matching.

Notification — NotificationDispatcher (interface) / LogNotificationDispatcher

  • The only seam for email/SMS/webhook. Currently logs ([scraper-notify:log] …); swap in a real impl behind the interface.
  • At-least-once: a match is marked notified only after a successful dispatch — a broken channel retries instead of losing the alert, and never blocks matching.

Export — HearingExportService

  • Reads the previous Mon–Sun window from both raw tables, merges into one sorted row set, writes a BOM-prefixed quoted CSV via temp-file + atomic rename (idempotent, never half-written).
  • Reads the DB only — a failed scrape still exports whatever exists.

Scheduling — ScraperScheduler + ScraperProperties

  • Three @Scheduled jobs (daily 10:05 Mon–Fri, weekly 10:15 Mon, export 10:30 Mon), all gated by scraper.enabled and overridable via the cron properties.
  • ScraperProperties binds the whole scraper.* block (see §9 Configuration).

5. Weekly CSV export (new)

Every Monday 10:30 (scraper.export-cron), HearingExportService writes the previous Monday–Sunday window (daily + weekly rows merged, same normalized schema) to:

export-dir/week-<monday>_<sunday>.csv     e.g. ./exports/week-2026-08-10_2026-08-16.csv
  • UTF-8 with BOM — Excel renders the Devanagari text correctly (a CSV without it opens as mojibake).
  • All fields quoted — party names and subjects contain commas, so quoting is mandatory.
  • matched column — Y/N flag marking rows that appear in hearing_matches (i.e. one of our cases).
  • Columns: courtId, hearingDateBs, hearingDateAd, caseNoBs, caseNoInternal, bench, serialNo, judgeName, subject, plaintiff, defendant, orderType, source, matched, sorted by court then date.
  • Idempotent — same file name per week; writes to a .tmp then atomically renames (never a half-written file). Re-running overwrites.
  • The export is independent of the scrape — it only reads the DB, so a failed scrape still exports whatever exists.

Configurable: scraper.export-dir (default ./exports). Directory is created if missing.

8. Frontend consumption guide

  1. Register a case — add a row to scraper_client_cases (courtId + caseNoInternal + ACTIVE). No CRUD endpoint exists yet; until one is added, register via DB/seed. Once registered, the court is scraped automatically.
  2. Show a case's hearing status — call GET /api/v1/cases/{caseNoInternal}/hearing-status whenever a case screen opens. Fast, DB-only, shows upcoming + history with judge, subject, outcome and source.
  3. Notifications — new matches are logged ([scraper-notify:log]) and stored in hearing_matches (field notified). A future real channel (email/SMS/webhook) plugs into the NotificationDispatcher interface; until then, poll the hearing-status endpoint or read matches.
  4. Weekly snapshot — the CSV file is a human-facing artifact (open in Excel; Nepali text renders because of the BOM). Not needed by the frontend unless you add a download link to POST /api/v1/scraper/admin/export.
